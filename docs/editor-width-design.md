# 正文宽度设计

设置入口:设置 → 外观 → 「正文宽度」。本文档记录该功能的模型、参数依据与方案迭代过程,供后续评估与调整参考。

## 背景与目标

正文排版宽度旧版为固定 850px 上限:编辑区不足 850px 时占满,超过后正文恒为 850px 居中。该值在中小窗口下观感合适,但存在两个问题:

1. 大屏、全屏或收起侧栏时,正文相对编辑区偏窄,两侧留白过大;
2. 上限不可调,不同尺寸显示器上无法统一「正文占编辑区的比例」。

目标:正文宽度可调;调宽时大屏受益明显;常规窗口下不改变现有排版观感。

## 最终模型

正文内容块宽度 = **min(编辑区宽, max(基准宽, 比例 × 编辑区宽))**

- 编辑区宽 = 工具栏与正文所在区域(.editor-main)的可用宽度,计算时扣除正文滚动条 12px;
- 两段式:编辑区不宽时按基准上限(与旧版固定上限行为一致);编辑区超过基准后,按比例随编辑区线性放大,不再封顶。

### 三档参数

| 档位       | 基准宽 | 放大比例 | 常规窗口文字区(16px 字号) |
| ---------- | ------ | -------- | ------------------------- |
| 适中(默认) | 850px  | 60%      | 约 46 字/行               |
| 宽         | 1000px | 70%      | 约 55 字/行               |
| 占满窗口   | 无上限 | 100%     | 随编辑区                  |

### 场景行为对照

以 1440 逻辑宽全屏为例(滚动条修正后为近似值):

| 场景                      | 编辑区约 | 适中 | 宽        | 占满 |
| ------------------------- | -------- | ---- | --------- | ---- |
| 文件树 + 大纲全开         | 950      | 850  | 938(顶满) | 938  |
| 只开大纲                  | 1190     | 850  | 1000      | 1178 |
| 无面板                    | 1430     | 857  | 1000      | 1428 |
| 带鱼屏 1720 逻辑宽,无面板 | 1708     | 1025 | 1196      | 1708 |

性质:

1. 编辑区不超过基准时,各档与旧版固定上限观感一致(宽档顶满属空间不足,非缺陷);
2. 编辑区越宽,三档差异越大;窄编辑区下档位趋同是空间上限的物理约束;
3. 大屏上正文按比例放大,不同显示器「正文占编辑区比例」趋于一致。

## 方案迭代记录

1. **固定像素三档(850 / 1100 / 占满)**:实现最简单,但固定上限在大屏上依旧封顶,最初的问题(大屏正文偏窄、跨显示器不一致)未解决。
2. **纯比例(60% / 70% / 100%)**:编辑区被文件树、大纲挤占时,正文被同比例压窄(极端场景文字区缩水约三分之一),且各档计算结果撞到同一下限保护,档位失效。
3. **基准宽 + 比例两段式(当前)**:中小编辑区用基准锚定旧观感,大编辑区用比例保证跨显示器一致性。纯定额与纯比例的缺陷各由另一段补足。

「宽」档基准最初定 1100px,实测「全屏 + 只开大纲」(编辑区约 1190)场景下 1100 几乎贴边,文字区 988px、一行 60 余字,超出舒适阅读范围,且与占满档仅差约 90px、层次不清,故收紧至 1000px。

## 关键取舍

- **不用 CSS 百分比,由 JS 统一计算**:工具栏、查找替换条、外部更新横幅按「正文宽度 − 内边距」与正文对齐,百分比在各自容器中解析基准不一致,会造成对齐散架。由单一入口把档位换算为像素写入 `--editor-max-width`,所有跟随元素严格对齐;编辑区尺寸变化(窗口缩放、拖动侧栏)经 ResizeObserver 实时重算。
- **「占满」用无上限基准表达**:等价于取消限宽,只保留两侧内边距;不用极大像素值或 `none`,避免下游 `calc()` 语义问题。
- **默认档保持旧观感**:850px 基准对多数文档仍是合理的可读行宽(一行约 46 个中文字),新设置只服务有更大空间需求的场景。
- **内边距不参与比例缩放**:两侧 56px 内边距固定,留白的主要来源是居中后两侧的空隙,随比例自然伸缩;窄窗口下内边距占比偏高的问题暂不处理,待实际反馈再评估。

## 开放问题

1. **参数手感**:1000px、0.6 / 0.7 的取值基于当前少量场景验证,长期是否合适需更多使用反馈;若频繁手动微调,可考虑升级为像素滑块或自定义输入(Obsidian 的可读行宽模式),代价是多一套数值 UI 与校验。
2. **档位数量**:三档是否够用;「更宽 1400px」这类中间档在多大屏上有独立价值存疑。
3. **比例接管点**:比例项在编辑区超过「基准 ÷ 比例」后才生效(适中约 1417px、宽约 1429px),若日常编辑区恰在此附近,档位间差异会长期不明显。
4. **内边距策略**:窄窗口下 56px 内边距占比偏大,是否引入响应式内边距(窄窗口收窄)待评估。
